# Voie Libre: context for Claude Code

Read this file, [BRIEF.md](BRIEF.md) and [PLAN.md](PLAN.md) at the start of each session. Architecture lives in [docs/architecture.md](docs/architecture.md).

## What this is

Open-source (AGPL-3.0) route planner for road/gravel cycling and trail running, as a website and later an Android app (Capacitor). Local first: routes live on the device; sending anything to the server is always the user's choice. At launch the only user is the author.

## Stack (fixed)

- **Front** (`apps/web`): Angular single-page app, no SSR, strict TypeScript, standalone components, signals. MapLibre GL JS used directly. Transloco for i18n at runtime.
- **API** (`apps/api`): Node.js, Fastify, TypeScript. TypeBox schemas with `@fastify/type-provider-typebox`; OpenAPI generated by `@fastify/swagger` (spec on `/openapi.json`, UI on `/docs`). `@fastify/rate-limit` and `@fastify/cors` are registered.
- **Client** (`packages/api-client`): TypeScript types and `openapi-fetch` client generated from `/openapi.json`. Never edit `src/schema.d.ts` or `openapi.json` by hand: run `npm run generate-client`.
- **Map**: `MapView` (`apps/web/src/app/core/map`) uses MapLibre directly, lazy-loaded. The basemap (`basemap.pmtiles`: France by default, about 4.7 GB at zoom 14, fonts, sprites in `data/basemap`) is served locally by the `tiles` compose service (`docker/tiles/default.conf`: responses are cached for an hour, errors never, so a 404 seen before a download ended cannot leave the map empty); the app reads only the bytes it shows (range requests), so a bigger area costs the user nothing; when the map is centred outside the archive's box (read from its header, `basemapBounds`, `BASEMAP_COVERAGE`) a note says there is no map data there; the map must never call an external domain, except the IGN's aerial photos once the user ticks them (see Aerial photos below). Map controls and attribution are Angular elements so they are translated.
- **Relief and layers** (`core/map/basemap-style.ts`, `map-layers.ts`, `scripts/build-relief-tiles.ts`, `libs/shared/src/lib/relief-tiles.ts`; see `BRIEF-relief.md`): `npm run build-relief` turns the Copernicus GeoTIFFs of `data/relief` into `data/basemap/relief.pmtiles` (terrarium PNG tiles of 512 px, zooms 6 to 11, elevations rounded to 0.25 m, over the squares of the files (or `RELIEF_BBOX`); MBTiles written with `node:sqlite`, converted by the `pmtiles` CLI or its Docker image). `scripts/download-relief.sh france` fetches the 133 Copernicus squares of France (4.6 GB; 17 of the 150 are open sea); the build reads them through `CellStore` (`libs/shared/src/lib/cell-store.ts`: files read when a tile needs them, a dozen kept, a square with no file reads as sea level), about 9,000 tiles, 1.8 GB, about an hour (see `BRIEF-relief-france.md`). Outside the relief file the hillshade is absent (the basemap alone). `buildBasemapStyle(base, language, { relief })` adds a `raster-dem` source and one `hillshade` layer under `water`. `MapView` creates the map without relief, then asks whether the archive exists (the offline copy, else a `HEAD` request behind the `RELIEF_PROBE` token; `provideFakeMap(maps, { relief })` in tests) and restyles with `setStyle` when the language or the relief changes (the planner's layers come back on `styledata`). The layer switcher is an Angular control under the zoom buttons (two checkboxes: Relief, disabled with a note when there is no archive, and Ways for the profile, disabled while `MapView.waysProfile` is empty); the choices live in `MapLayers` (`localStorage`, relief on and ways off by default, never sent). **Ways for the profile** (`core/map/way-levels.ts`, see `BRIEF-ways.md`): with the checkbox on, `buildBasemapStyle(..., { ways })` adds three line layers (`ways-avoid`, `ways-fair`, `ways-good`) over the Protomaps `roads` layer and under the first label, filtered on `kind_detail` by a table per profile (`wayLevel`); `Planner` passes the selected profile, so the map follows it; the ways to avoid are dashed and a legend shows in the switcher. `usableBy` (snapping) is a separate rule and still accepts trunk roads on Road. The attribution names Copernicus while the relief is shown. Other layers are only proposals (`docs/map-layers.md`).
- **Aerial photos** (`core/map/basemap-style.ts`, `map-layers.ts`, `map-view.*`; see `BRIEF-imagery.md`): the one opt-in exception to the local map. `MapLayers.imagery` (off by default, kept on the device) has `buildBasemapStyle(..., { imagery })` add a raster source on the IGN Géoplateforme (`IMAGERY_TILES`, `IMAGERY_HOST` = `data.geopf.fr`, layer `ORTHOIMAGERY.ORTHOPHOTOS`, 256 px JPEG, zooms 6 to 19, no key, CORS open) and a raster layer right after the background; every `fill` layer of the basemap is dropped so the photos show, the roads, the ways of the profile and the names stay over them, and the relief goes right over the photos. The switcher's note says the IGN server sees the user's address and the area looked at (no confirmation dialog: ticking is the consent); the checkbox is disabled while `NetworkStatus` is offline and the map goes back to the local style by itself. The photos are never cached (not in `ngsw-config.json`, not in "Download the map"). The attribution adds "Photos: IGN" while shown (Licence Ouverte Etalab 2.0). France only.
- **Failed tiles** (`apps/web/src/app/core/map/failed-tiles.ts`): MapLibre never retries a tile in error while it stays on screen; `retryFailedTiles` asks it again after a growing delay (`MAX_RETRIES`) and once more each time the map stops moving.
- **Planner** (`apps/web/src/app/planner`): `PlannerStore` holds the state and the pure rules (points, profile, alternatives, result); `RoutePlanner` recomputes through the generated client with a debounce and aborts stale requests; a `PlannerMapDriver` draws markers and routes (real one in `maplibre-driver.ts`, fake in tests). API error codes are translated under `planner.errors.*`; never show a raw API message. **Map interaction** (see `BRIEF-map-interaction.md`): `PlannerStore.nextRole` says what the next click creates (shown by the ghost marker under the mouse, `PlannerMapDriver.setGhost`: A, B or a "+" for a stop, whose number is only known once it is placed, and by the help bar); markers differ by shape and colour, a loop is one combined marker (`isLoop`); `insertPoint`, `closeLoop`, `setStart`/`setEnd`; the start marker of an open route offers to close the loop (`closable`) and a dialog lets the user pick how (the button says "Make a loop" with only a start and "Close the loop" with a route, `Planner.loopLabelKey`, with a one-line hint under it, `planner.loop.make`/`close` and `makeHint`/`closeHint`, also the dialog's title): back to the start, avoid the way out (`loop: {mode: 'avoid_outbound'}`: the API routes the way out, then the way back with the way out as a simplified polyline no-go, `routing/loops.ts`; falls back to the plain way back), or a loop by distance (`loop: {mode: 'distance', distanceMeters}` with the start twice: `RoutingProvider.roundTrip`, BRouter round trip with its radius corrected over up to 3 calls, alternatives head in evenly spaced directions, or close to the optional `direction`, one of 8 compass points chosen in the dialog; length and direction editable in the panel; `PlannerStore.loop` drops the mode once edits no longer fit it); dragging the selected route inserts a waypoint in the right segment (`insert-point.ts`), and so does a click on the map (or "Add a stop here" in its menu, or "My position") while a route is on screen and up to date: `Planner.addStopAt` puts the point between the two points whose stretch of the route is the closest to it (`insertionIndex`), before the end only for the last stretch, or when no route is on screen (still computing, in error, fewer than two points); right click or long press on the map opens a menu (set start, add stop, set end), long press on a marker removes it, with an undo toast (`PlannerStore.removed`).
- **Local edits** (`apps/web/src/app/planner/local-edit.ts`, `RoutePlanner`): adding, inserting, moving or removing a point on a route that is on screen recomputes only a stretch around it (see `BRIEF-local-edits.md`). `PlannerStore` records each change as a `PointEdit` (`editBehind(points)` is non-null only while the points are those it produced; moving both ends of a loop records none); `planLocalEdit` (pure) gives the window (`max(500 m, 2 × distance from the point to the route)` each side, clamped to the neighbouring points) and the points of the short `POST /route` (route vertex before, the point, route vertex after; one alternative, no `loop`); `PlannerStore.applyLocalEdit` splices the answer (`applyStretch`: totals from the kept parts), keeps only the selected alternative and marks the inputs as restored. Removing a stop is the exception to the window: the whole way between its two neighbours is replaced by a route from one to the other (full computation when they are the same place, the only stop of a loop). Full computation stays for: profile or alternatives change, a route not up to date with the points (still loading, or in error: `setLocalEditError` keeps the route on screen), a start or end removed, a loop's start moved. Two edits before the first answer arrives compute in full.
- **Live drag** (see `BRIEF-backlog.md`): while a marker is dragged, or the route to pull a waypoint out of it, the driver reports each place (`onDragStart`, `onDragPoint`, `onDragInsert`) and does not draw the markers again (`setMarkers` is deferred until the drop). `Planner` paces the places (`LIVE_DRAG_INTERVAL_MS` = 600, never before the previous answer; the insertion segment is found once, on the route the drag started from) and passes them to `PlannerStore.dragTo`: always an edit of the points and route the drag started from (`startDrag` keeps them; `routeBehind`), so each one is a local edit and nothing piles up. `RoutePlanner` skips its debounce while `store.dragging()`. The drop (`endDrag`) is one step of history; Escape (`cancelDrag` on the driver, then on the store) puts the points and the route back. No undo or redo key and no address lookup (`PointNamer`) during a drag. The default `ROUTE_RATE_LIMIT_MAX` (120 a minute) leaves room for it.
- **Undo and redo** (`PlannerStore`, buttons and keys in `Planner`; see `BRIEF-undo.md`): every change to the route being planned (points, clear, profile, alternatives, loop mode, length and climb of a loop by distance) pushes a `Snapshot` (inputs plus the routes on screen, or `null` routes when they were not those of the points: `routesFor` holds the signature they were computed from) on a stack of `HISTORY_DEPTH` = 20. `undo()`/`redo()` restore it without any `POST /route` (the inputs are marked as restored); a snapshot without routes computes as for any change. Ctrl/Cmd+Z undoes, Ctrl/Cmd+Shift+Z and Ctrl+Y redo, ignored in text fields, selects and while the loop dialog is open. `loadSaved` empties the history; opening a saved route or importing a GPX is not undoable. An edit made before the previous one's route is in place is never local (`lastEditFromRoute`).
- **Place search** (API `geocoding/`, `routes/geocoding.ts`; web `apps/web/src/app/search`; see `BRIEF-search.md`): `Geocoder` interface, `PhotonProvider` (public server by default, `GEOCODER_URL`; only the API calls it). `GET /geocode?q=&lang=&lat=&lon=` and `GET /geocode/reverse` (rate limited, `GEOCODE_RATE_LIMIT_MAX`). The panel has Start and End fields (`PlaceField`: combobox, 300 ms debounce, disabled offline through `NetworkStatus` and while there is no start) and a reverse button (`PlannerStore.reverse`: the whole list of points reversed, stops included, a full recompute; a loop with two stops or more goes round the other way, `canReverse` is false for a loop with fewer); picking a place calls `setStart`/`setEnd`, `setLabel` and `PlannerMapDriver.centerOn`. Each stop is a `PlaceField` too, between the two (a place picked there moves the stop; a handle on its left, made of the grip dots and the stop's number, reorders it: the field gets `bareMarker`; a button on the right removes it). A "+" between each pair of fields opens an empty field there (`Planner.newStopAt`, the index the stop will take; closed when the points change), for a stop to search. An empty field offers "My position" as its first choice, which sets that point from `LocationStore` (asking for the position if needed). Place names live in `PlannerStore.labels`, keyed by coordinates (with `shortOf`: the short name the API gives each place, `Place.short`: its own name when searched, its town or village for an address or a click) (so they follow their point through undo, reorder and swap, and never recompute a route; not stored in saved routes). `PointNamer` reverse-geocodes the start and the end when they have no name (click, drag, menu, position), once per place, never offline; failures keep the coordinates. Errors are translated under `planner.search.errors.*`.
- **Points on ways** (`apps/web/src/app/planner/snap-to-way.ts`, `way-snapper.ts`, `apps/web/src/app/core/map/way-tiles.ts`; see `BRIEF-reverse-fit-snap.md`): on Road and Gravel a point placed on the map (click, map menu, marker drop, waypoint pulled out of the route, each place of a live drag) lands on the nearest way the profile can use (`usableBy`: classes of the Protomaps `roads` layer), within `SNAP_MAX_METERS` (100) and `SNAP_MAX_PIXELS` (24, `PlannerMapDriver.metersPerPixel`); with none that close the point is refused (`Planner.refused`, message `planner.snap.refused`; a refused drop cancels the drag) and during a live drag the route stays on the last valid place. Trail is never snapped; nor are places from the search, "My position", imports, or places where the basemap has no tile. The ways are read from the zoom 14 tile around the point (`WAY_TILE_ZOOM`: lower zooms leave small roads out) through the map's own PMTiles reader (`basemapTileReader`, offline copy first, no other server), decoded with `@mapbox/vector-tile` and `pbf`, behind the `WAY_TILES` token (`null` reader, so no snapping, while there is no real map: tests set a fake). `WaySnapper.peek` answers at once from the tiles already read, `snap` reads them first; the ghost marker shows the landing place (`PlannerMapHandlers.ghostAt`).
- **Profile choice** (`apps/web/src/app/planner/profile-select.*`): `ProfileSelect`, a select-only combobox (the focus stays on the button, `aria-activedescendant`) where each profile has a title and a description (`planner.profile.<id>.title` and `.description`); a native select cannot show two lines per option.
- **Elevation profile** (`apps/web/src/app/planner/elevation-profile.ts`, `elevation-panel.*`): `buildProfile` (pure: cumulative distance, grade over a 50 m window) and `ElevationPanel` under the map. The chart is coloured by grade bands (`GRADE_BANDS`, `gradeRuns`; the route line on the map keeps its colour). Dragging over the chart (or Shift+arrows) selects a stretch: `stretchStats` gives its distance, ascent, descent and average grade, `PlannerStore.stretch` holds it (dropped as soon as the selected geometry changes) and `PlannerMapDriver.setHighlight` draws it on the map; a click or Escape clears it. The shared cursor is `PlannerStore.cursor` (index in the selected geometry): the panel sets it on pointer or keys, `Planner` sets it from `PlannerMapDriver.onHoverRoute`, and an effect shows it as a dot through `setCursor`.
- **Surface of the route** (API `routing/surface.ts`, web `planner/route-surface.ts`, `core/map/surface-categories.ts`; see `BRIEF-surface.md`): `RouteResult.surfaces` and the `POST /route` response carry one character per segment of the geometry (`geometry.length - 1`): `p` paved, `c` cycleway, `u` unpaved or rough (cobbles included), `s` path, `?` unknown. `classifyWay` reads BRouter's `WayTags` (the surface first, then the way class), `surfacesFromMessages` lines the messages up with the geometry by their end coordinates and leaves `surfaces` out when they do not fit. `trimSpurs` and the "avoid the way out" join keep it in step. Web: `PlannedRoute.surfaces` is optional (imported files, routes saved before, shared routes have none), `applyStretch` splices it like the geometry (`spliceSurfaces`; it is dropped if the stretch has none), saved routes store it. `ElevationPanel` draws a bar under the chart on the chart's distance scale with the share of each category (`surfaceShares`); the checkbox "Surface of the route" of the layer switcher (`MapLayers.surface`, off by default) has `Planner` call `PlannerMapDriver.setSurfaces`, which draws the selected route in the categories' colours over its line (`surfacesToGeoJson`). A route without surfaces (saved before, imported, shared) says so (`PlannerStore.surfaceMissing`: a note under the chart and in the switcher) and offers "Calculate the surface": `PlannerStore.recompute` computes the route again from its points (`recomputeCount` makes `RoutePlanner` run with the same inputs), one step of history, so Undo brings the saved route back, and a failure keeps the route on screen (`takeRefresh`, `setLocalEditError`); `canRecompute` is false for a route from a place to itself without a loop mode, which gets a note and no button. Saved routes keep the loop mode they were computed with (`SavedRoute.loop`, optional: `PlannerStore.savable` gives it, `loadSaved` restores it and the restored signature includes it, so opening still computes nothing); loops saved before that kept none and stay as they are; opening a route still never computes.
- **User position** (`apps/web/src/app/location`): the user shares it with the "My position" button on the map; it stays in memory (`LocationStore`: status, fix, error code), never stored, logged or sent to the API. The source sits behind the `GEOLOCATION` token (browser `watchPosition`; a fake in tests, a Capacitor plugin later). `PlannerMapDriver.setLocation` draws a blue dot, the accuracy circle (`accuracyCircle`, a map layer) and a cone when `coords.heading` is known, and moves the view to the first fix only. "My position" in the panel and the map menu adds a point at the fix like a click would (`addPoint`). Errors are `LocationErrorCode`s translated under `location.errors.*`; the button is disabled outside a secure context.
- **GPX import** (`apps/web/src/app/import/gpx-import.ts`, button in `saved-routes`): `parseGpx` (DOMParser, `querySelectorAll`: live collections are quadratic in jsdom) reads the first `<trk>` (segments joined) else the first `<rte>`; geometry thinned to 5000 points, climb with a 3 m threshold, duration estimated per profile. No elevation on every point → `ascentMeters: null` (type `number | null` on `PlannedRoute`/`SavedRoute`): the profile is hidden, sharing is disabled, `buildGpx` gets `withElevation: false`. Errors are `GpxImportError` codes translated under `gpxImport.errors.*`.
- **Relief** (API `relief/`, `routes/elevation.ts`; web `relief/elevation.service.ts`): `ElevationProvider` interface, `CopernicusElevationProvider` reads Copernicus GLO-30 GeoTIFFs from `RELIEF_DIR` with `geotiff` (one window read per tile, bilinear, `null` outside the tiles or on no-data). `POST /elevation` (max 5000 points, `ELEVATION_RATE_LIMIT_MAX`). The web app calls it only when the user asks to compute the climb of an imported route (`ElevationService.forGeometry`, gaps interpolated, refused under 80% coverage); `RouteStore.setElevation` stores the result. Jest transforms the ESM-only dependencies of `geotiff` (see `jest.config.cts`). The real-data spec skips itself without the tiles.
- **Credits**: `PlannedRoute.elevationSource` (`'srtm'` for BRouter routes, `'copernicus'` once the climb was computed from tiles; absent for an imported file's own elevations) is stored with the saved route and shown under the profile (`profile.source.*`).
- **Local storage** (`apps/web/src/app/storage`, `saved-routes`): saved routes live in IndexedDB (native API) behind the `RouteStore` interface, injected with the `ROUTE_STORE` token (SQLite can replace it under Capacitor). Only the selected itinerary is stored, with a `schemaVersion`; ids are 10 random characters. Opening one goes through `PlannerStore.loadSaved`, which must never trigger `POST /route` (`RoutePlanner` skips inputs matching the restored route until the user edits). Storage failures are `RouteStoreError` codes translated under `saved.errors.*`; the planner stays usable without storage.
- **GPX and FIT export** (`apps/web/src/app/export`): `buildGpx` (pure, GPX 1.1, one `<wpt>` per route point with translated names, then one track) and `buildFit` (`fit.ts`, pure, no dependency: a FIT course file with `file_id`, `course` (running for Trail, cycling otherwise), one `lap`, timer events, one `record` per geometry point and one `course_point` per stop; times are made up from the estimated duration; no altitude when the climb is unknown) turn a saved route's stored geometry into a file on the device. The "Export" button of a saved route opens the choice of a format (`exportingId`, `exportAs`); the download goes through the `FILE_DOWNLOADER` token (text or bytes; browser link now, Capacitor share later). Never built by the API. `fit.spec.ts` reads the file back with `fit-file-parser` (dev dependency only).
- **Offline** (`apps/web/src/app/core/offline`, `ngsw-config.json`): `@angular/service-worker` (production build only) prefetches the app shell and the i18n files, and keeps the basemap's glyphs and sprites (`dataGroups`, matched on any host by the `/fonts/**` and `/sprites/**` patterns of `ngsw-config.json`). The PMTiles archive is far too big to copy, so the user keeps **areas** (`OfflineBasemap`, panel `OfflineMap`; see `BRIEF-coverage.md`): the corridor of 5 km each side around the route on screen (`corridorTiles`, `AREA_BUFFER_METERS`) or the view on screen (`MapViewport`, `viewBox`), zooms 0 to 14 (`core/offline/area-tiles.ts`, pure). `plan` samples tiles of the basemap and of the relief to estimate the size and checks the room (`navigator.storage.estimate`); an area above `AREA_MAX_BYTES` (1 GB) or `AREA_MAX_TILES` is refused (`too_big`); `keep` reads every tile through the PMTiles reader with a `RecordingSource`, which stores each byte range it got (header, directories, tiles) in a Cache Storage cache of its own (`voie-libre-area-v2-<id>`, key `url?vl-range=offset-length`); the list of areas (name, size, box, relief or not) is in `localStorage`. `OfflineFirstSource` reads the kept range first (`caches.match` looks through every area cache) and the network otherwise, so the map needs no network inside a kept area; removing an area deletes its cache; a cache the browser evicted drops its area from the list; the cache of the first version (whole archive) is deleted when found. The relief tiles of the area come along when the server has a relief archive (a 404 means none). Check offline with `npm run serve:prod` (`scripts/serve-static.mjs`: static files with an `index.html` fallback; the service worker does not run in `npm run dev`). `AppUpdate` + `vl-update-prompt` offer to reload when the service worker has a new version ready (never reload by themselves). When the network cannot carry a request, the service worker answers 504: the API error mappers treat 504 as network/unavailable.
- **Saved routes list**: the name button is stretched over the whole card (`::after`), so a click anywhere opens it; when the route on screen is unsaved work (`PlannerStore.unsaved`: points whose inputs differ from those of the route last saved or opened, `markSaved`, `savedSignature`) a confirmation comes first; a saved route opened and left alone, one just saved, or an edit that was undone, is replaced at once. Hovering a card shows its trace through `PlannerStore.preview` and `PlannerMapDriver.setPreview` (no view change). The steps in the planner panel are reordered with their grip (a button; see `BRIEF-reorder.md`): pointer events, not native drag and drop, so mouse and finger behave alike (`Planner.onGripDown`, `reorder` signal, `numberOf` gives each row's future place as its CSS `order`: the rows show the new order while dragging, the numbers and the "+" stay (the "+" inert), the help bar says the route is computed again, Escape or a cancelled pointer changes nothing); Arrow Up/Down move a stop at once and a live region announces it. Release or key calls `PlannerStore.reorderPoint` (a full recompute, undoable). **Name proposed for a route** (`planner/route-name.ts`, `saved-routes`; see `BRIEF-route-names.md`): the name field proposes `A → B`, `A → B via S`, `A → B via 3 stops`, `Loop around A` or `Around A` from the short names of the places (`autoRouteName`, keys `saved.autoName.*`), `Road, 41 km` while a name is unknown; the proposal follows the route until the user types in the field, and never again for this route; emptying the field saves the proposal; clearing the route or saving brings the automatic name back; a name already taken gets the date, then ` (2)`. Only the start and the end are looked up (`PointNamer`: a lookup running is cancelled only when its place stops being an end), so a stop has a name only when it was picked by search.
- **Sharing** (API `routes/shared.ts`, `db/shared-routes.ts`; web `sharing/`): no account. `PUT /p/{id}` creates a shared route under the id drawn on the device and returns a delete token once (only its SHA-256 is stored); shared routes are **immutable** (an existing id answers 409, no update); `GET /p/{id}`, `GET /p/{id}.gpx?lang=`, `DELETE /p/{id}` with `Authorization: Bearer <token>`. PUT is throttled hard (`SHARE_RATE_LIMIT_*`) and capped (`SHARE_BODY_LIMIT_BYTES`, 5000 geometry points, 20 points). The token stays in the local record (`SavedRoute.share`), never in a URL or on screen. The share button is hidden for now (`SHARING_ENABLED` token, default `false`); the API and the code stay. Sharing is always an explicit user action; deleting a shared route unshares it first. `/p/:id` in the web app (`SharedRoutePage`) opens a link through `PlannerStore.loadSaved`, without computing or storing. GPX building and the id alphabet live in `libs/shared` (used by both).
- **Design** (see `BRIEF-design.md`, `PLAN-design.md`, `docs/design-tokens.md`): direction "C3 Dossard", light theme only. `apps/web/src/design-tokens.css` holds the tokens (colour, map palette, type, space, radius, shadow, 44 px target, focus ring); no hex or `rgb()` in a component stylesheet, read `var(--...)`. `styles.scss` styles native buttons, fields and selects once with `:where()` (a component rule wins) and sets the focus ring. The map and chart colours live in `core/map/palette.ts` (MapLibre cannot read custom properties) and are repeated in the tokens file; `palette.spec.ts` fails if they differ, so change both. Header: green bar with the "VL" bib logo (`public/icons/logo.svg`, source of the favicon and app icons) and the word mark. The planner panel has two sections (Route, Saved) and is a bottom sheet under 40 rem (`sheetOpen`; its handle, 44 px targets); the profile choice is a radio group of sport pictograms (`ProfileSelect`); the elevation panel starts closed on a phone. System fonts only (the map calls no external domain).
- **Data**: PostgreSQL + PostGIS. Migrations with node-pg-migrate in `apps/api/migrations` (SQL files).
- **Routing**: BRouter behind the `RoutingProvider` interface (`apps/api/src/routing`). BRouter kills a running request when more than its thread count arrive at once, so `BRouterProvider` queues its calls (`BROUTER_MAX_CONCURRENT`); an alternative the engine cannot find is left out, an error comes only when there is no route at all. GraphHopper may come later for loops. External components (routing, geocoding, tiles, relief) always sit behind interfaces.
- **Monorepo**: Nx (integrated mode) with npm. Shared code in `libs/shared`; path aliases in `tsconfig.base.json`.

## Rules

- Code, comments, commits, docs and README in English. UI in English by default with a French translation.
- **No hard-coded UI string.** Every label goes through Transloco keys in `apps/web/public/i18n/en.json` and `fr.json`; a test fails when a key is missing in one of them. Numbers, dates and units go through the `Intl`-based formatting layer (metric by default).
- **No secret in the repository.** Configuration comes from environment variables; `.env.example` lists them all with development defaults only.
- The API returns stable error codes; the web app translates them. Validate requests and responses with schemas.
- Small verified steps: follow PLAN.md, commit once per step in English with a conventional message (`feat:`, `chore:`, `docs:`) after lint, build and targeted tests pass.
- Out of scope for milestone 1: accounts and sync, avoid zones and reports, Android APK.

./scripts/download-segments.sh && ./scripts/download-basemap.sh && ./scripts/download-relief.sh   # once: routing data, basemap, terrain
npm run build-relief        # once, after download-relief.sh: the map's hillshade tiles (data/basemap/relief.pmtiles)
docker compose up -d        # PostgreSQL/PostGIS, BRouter, tiles server

## General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
