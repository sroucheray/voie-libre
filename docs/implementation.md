# How the app is built, area by area

The detail behind the one-line summaries of [CLAUDE.md](../CLAUDE.md): files, names, thresholds and the choices that are easy to break. Each section was written when its feature landed; the brief of a feature and how it went are in [features](features/README.md).

## Map

`MapView` (`apps/web/src/app/core/map`) uses MapLibre directly, lazy-loaded. The basemap (`basemap.pmtiles`: France by default, about 4.7 GB at zoom 14, fonts, sprites in `data/basemap`) is served locally by the `tiles` compose service (`docker/tiles/default.conf`: responses are cached for an hour, errors never, so a 404 seen before a download ended cannot leave the map empty); the app reads only the bytes it shows (range requests), so a bigger area costs the user nothing; when the map is centred outside the archive's box (read from its header, `basemapBounds`, `BASEMAP_COVERAGE`) a note says there is no map data there; the map calls no external domain except two, both named and both on the user's side of a checkbox: the public AWS terrain tiles of the hillshade (on by default, see Relief and layers) and the IGN's aerial photos (off by default, see Aerial photos). Map controls and attribution are Angular elements so they are translated. A change of style (language, layers) is applied only once the style is done loading (`isStyleLoaded`, else it waits for `styledata`): asked earlier, MapLibre logs "Unable to perform style diff" and rebuilds the style from scratch, which the default-on layers made happen at every start.

## Relief source

(`core/map/relief-source.ts`, `relief-protocol.ts`; see `docs/features/relief-public.md`): by default (`RELIEF_SOURCE_KIND` = `'public'`) the hillshade reads the public AWS Terrain Tiles (`https://s3.amazonaws.com/elevation-tiles-prod/terrarium/{z}/{x}/{y}.png`: Terrarium PNG of 256 px, no key, CORS open, data last modified in 2017) through a `vlterrain://{z}/{x}/{y}` protocol of MapLibre registered in `map-factory.ts`: a tile kept in an offline area first (found by `caches.match` under its public URL), the server otherwise. The source stops at zoom 12 (`PUBLIC_RELIEF_MAX_ZOOM`: the data is about 30 m apart, which zoom 12 shows already; deeper zooms are drawn from those tiles), so an area kept offline (zooms 6 to 12 of its zone, `PUBLIC_RELIEF_OFFLINE_*`, counted in the size estimate and stored in the area's own cache) covers every zoom. A note under the "Relief" checkbox says Amazon's server sees the user's address and the zone looked at; the credit links to Mapzen's list of sources (`RELIEF_CREDIT_URL`). With `'local'` nothing changes from the earlier design below (own archive, probe, ranges kept in the areas); `provideFakeMap` defaults the tests to `'local'`.

## Relief and layers, local source

(`core/map/basemap-style.ts`, `map-layers.ts`, `scripts/build-relief-tiles.ts`, `libs/shared/src/lib/relief-tiles.ts`; see `docs/features/relief.md`): `npm run build-relief` turns the Copernicus GeoTIFFs of `data/relief` into `data/basemap/relief.pmtiles` (terrarium PNG tiles of 512 px, zooms 6 to 11, elevations rounded to 0.25 m, over the squares of the files (or `RELIEF_BBOX`); MBTiles written with `node:sqlite`, converted by the `pmtiles` CLI or its Docker image). `scripts/download-relief.sh france` fetches the 133 Copernicus squares of France (4.6 GB; 17 of the 150 are open sea); the build reads them through `CellStore` (`libs/shared/src/lib/cell-store.ts`: files read when a tile needs them, a dozen kept, a square with no file reads as sea level), about 9,000 tiles, 1.8 GB, about an hour (see `docs/features/relief-france.md`). Outside the relief file the hillshade is absent (the basemap alone). `buildBasemapStyle(base, language, { relief })` adds a `raster-dem` source and one `hillshade` layer under `water`. `MapView` creates the map without relief, then asks whether the archive exists (the offline copy, else a `HEAD` request behind the `RELIEF_PROBE` token; `provideFakeMap(maps, { relief })` in tests) and restyles with `setStyle` when the language or the relief changes (the planner's layers come back on `styledata`). The layer switcher is an Angular control under the zoom buttons (two checkboxes: Relief, disabled with a note when there is no archive, and Ways for the profile, disabled while `MapView.waysProfile` is empty); the choices live in `MapLayers` (`localStorage`, relief, ways and surface on by default and aerial photos off, never sent; a choice already kept on the device wins). **Ways for the profile** (`core/map/way-levels.ts`, see `docs/features/ways.md`): with the checkbox on, `buildBasemapStyle(..., { ways })` adds three line layers (`ways-avoid`, `ways-fair`, `ways-good`) over the Protomaps `roads` layer and under the first label, filtered on `kind_detail` by a table per profile (`wayLevel`); `Planner` passes the selected profile, so the map follows it; the ways to avoid are dashed and a legend shows in the switcher. `usableBy` (snapping) is a separate rule and still accepts trunk roads on Road. The attribution names Copernicus while the relief is shown. Other layers are only proposals (`docs/map-layers.md`).

## Aerial photos

(`core/map/basemap-style.ts`, `map-layers.ts`, `map-view.*`; see `docs/features/imagery.md`): the one opt-in exception to the local map. `MapLayers.imagery` (off by default, kept on the device) has `buildBasemapStyle(..., { imagery })` add a raster source on the IGN Géoplateforme (`IMAGERY_TILES`, `IMAGERY_HOST` = `data.geopf.fr`, layer `ORTHOIMAGERY.ORTHOPHOTOS`, 256 px JPEG, zooms 6 to 19, no key, CORS open) and a raster layer right after the background; every `fill` layer of the basemap is dropped so the photos show, the roads (drawn half transparent, their casing nearly gone: `ROADS_ON_PHOTOS_OPACITY`, `ROAD_CASINGS_ON_PHOTOS_OPACITY`, so they do not hide the ground), the ways of the profile and the names stay over them, and the relief goes right over the photos. The switcher's note says the IGN server sees the user's address and the area looked at (no confirmation dialog: ticking is the consent); the checkbox is disabled while `NetworkStatus` is offline and the map goes back to the local style by itself. The photos are never cached (not in `ngsw-config.json`, not in "Download the map"). The attribution adds "Photos: IGN" while shown (Licence Ouverte Etalab 2.0). France only.

## Failed tiles

(`apps/web/src/app/core/map/failed-tiles.ts`): MapLibre never retries a tile in error while it stays on screen; `retryFailedTiles` asks it again after a growing delay (`MAX_RETRIES`) and once more each time the map stops moving.

## Planner

(`apps/web/src/app/planner`): `PlannerStore` holds the state and the pure rules (points, profile, alternatives, result); `RoutePlanner` recomputes through the generated client with a debounce and aborts stale requests; a `PlannerMapDriver` draws markers and routes (real one in `maplibre-driver.ts`, fake in tests). API error codes are translated under `planner.errors.*`; never show a raw API message. **Map interaction** (see `docs/features/map-interaction.md`): `PlannerStore.nextRole` says what the next click creates (shown by the ghost marker under the mouse, `PlannerMapDriver.setGhost`: A, B or a "+" for a stop, whose number is only known once it is placed, and by the help bar); markers differ by shape and colour, a loop is one combined marker (`isLoop`); `insertPoint`, `closeLoop`, `setStart`/`setEnd`; the start marker of an open route offers to close the loop (`closable`) and a dialog lets the user pick how (the button says "Make a loop" with only a start and "Close the loop" with a route, `Planner.loopLabelKey`, with a one-line hint under it, `planner.loop.make`/`close` and `makeHint`/`closeHint`, also the dialog's title): back to the start, avoid the way out (`loop: {mode: 'avoid_outbound'}`: the API routes the way out, then the way back with the way out as a simplified polyline no-go, `routing/loops.ts`; falls back to the plain way back), or a loop by distance (`loop: {mode: 'distance', distanceMeters}` with the start twice: `RoutingProvider.roundTrip`, BRouter round trip with its radius corrected over up to 3 calls, alternatives head in evenly spaced directions, or close to the optional `direction`, one of 8 compass points chosen in the dialog; the length can be asked as a **duration** in the dialog (`loopBy`, `loop-duration.ts`: `distanceFor(minutes, speed)`; the speed is per profile, default road 22, gravel 17, trail 8 km/h, kept on the device by `LoopSpeeds`, never sent; the climb is ignored and the API still gets a distance; a saved loop reopens as a loop by distance), and the same dialog asks the number of alternatives (shared with the panel's `store.alternatives`); length and direction editable in the panel; `PlannerStore.loop` drops the mode once edits no longer fit it); dragging the selected route inserts a waypoint in the right segment (`insert-point.ts`), and so does a click on the map (or "Add a stop here" in its menu, or "My position") while a route is on screen and up to date: `Planner.addStopAt` puts the point between the two points whose stretch of the route is the closest to it (`insertionIndex`), before the end only for the last stretch, or when no route is on screen (still computing, in error, fewer than two points); right click or long press on the map opens a menu (set start, add stop, set end), long press on a marker removes it, with an undo toast (`PlannerStore.removed`).

## Open route

(see `docs/features/open-route.md`): a route can be **open**, its last point provisional, so that one can go from place to place without knowing the end. `PlannerStore.open` (private `openState`, only true with two points or more and no loop) is set by `clickPoint` (map click, "My position", the first two points) and cleared by `finish`, `setEnd` (typed or menu end: on an open route it appends the place and closes), `closeLoop`, `reverse`, `clear` and `loadSaved`; it is part of each `Snapshot`, so undo and redo bring it back, and `finish` / `continueRoute` are history steps. While open `appendPoint` adds after the last point (a `PointEdit` insert at the end: one stretch is computed), `Planner.addStopAt` routes clicks to `clickPoint` and the last point is drawn as a numbered stop (`MarkerSpec.finish`: the "Finish here" bubble, a button child of the marker element in `maplibre-driver.ts`, `PlannerMapHandlers.onFinish`; styles in `styles.scss`). `nextRole` is `start` then always `waypoint`. In the panel `stops` includes the last point, the end field gives way to an empty `.next-place` row (`pickNext`, "My position" target `next`), the last stop has a `.point-finish` tick, and a closed route that is not a loop shows `.continue-route` (`canContinue`); on a phone the sheet's peek has `.sheet-finish` beside the summary. Not saved with a route: a route opened from the saved list is closed.

## Local edits

(`apps/web/src/app/planner/local-edit.ts`, `RoutePlanner`): adding, inserting, moving or removing a point on a route that is on screen recomputes only a stretch around it (see `docs/features/local-edits.md`). `PlannerStore` records each change as a `PointEdit` (`editBehind(points)` is non-null only while the points are those it produced; moving both ends of a loop records none); `planLocalEdit` (pure) gives the window (`max(500 m, 2 × distance from the point to the route)` each side, clamped to the neighbouring points) and the points of the short `POST /route` (route vertex before, the point, route vertex after; one alternative, no `loop`); `PlannerStore.applyLocalEdit` splices the answer (`applyStretch`: totals from the kept parts), keeps only the selected alternative and marks the inputs as restored. Removing a stop is the exception to the window: the whole way between its two neighbours is replaced by a route from one to the other (full computation when they are the same place, the only stop of a loop). Full computation stays for: profile or alternatives change, a route not up to date with the points (still loading, or in error: `setLocalEditError` keeps the route on screen), a start or end removed, a loop's start moved. Two edits before the first answer arrives compute in full. **Stretch or whole route** (`shouldComputeInFull`, `FULL_COMPUTE_RULES` in `route-planner.ts`): not during a live drag, an edit is computed in full when the place was chosen on purpose (`PointEdit.deliberate`: a search, "My position"), when the route is under 50 km, or when the point is further than 2 km (or a tenth of the stretch between its neighbours) from the route; a click or move beside a long route, a removed stop and a live drag keep the stretch. A "Compute the whole route again" button (`PlannerStore.recompute`) asks for it all at any time.

## Live drag

(see `docs/features/backlog.md`): while a marker is dragged, or the route to pull a waypoint out of it, the driver reports each place (`onDragStart`, `onDragPoint`, `onDragInsert`) and does not draw the markers again (`setMarkers` is deferred until the drop). `Planner` paces the places (`LIVE_DRAG_INTERVAL_MS` = 600, never before the previous answer; the insertion segment is found once, on the route the drag started from) and passes them to `PlannerStore.dragTo`: always an edit of the points and route the drag started from (`startDrag` keeps them; `routeBehind`), so each one is a local edit and nothing piles up. `RoutePlanner` skips its debounce while `store.dragging()`. The drop (`endDrag`) is one step of history; Escape (`cancelDrag` on the driver, then on the store) puts the points and the route back. No undo or redo key and no address lookup (`PointNamer`) during a drag. The default `ROUTE_RATE_LIMIT_MAX` (120 a minute) leaves room for it. **On a touch screen** a tap puts no point (it still picks an alternative route) and a long press does, with a short vibration (`maplibre-driver.ts`, `touch-gesture.ts`; the right click keeps its menu); the help bar has `planner.hint.*Touch` variants. On a phone undo and redo are two buttons on the map, top left, and the elevation profile opens and closes with a swipe (`core/gestures/vertical-swipe.ts`; the whole profile bar toggles it). **Route tab layout** (see `docs/features/route-panel.md`): three blocks in the order of use. Start and end (profile, places, the loop card, then the loop settings of a loop by distance in a folded `details.loop-settings` whose title gives the length); **Route** (`.result`: its title with "Recompute" as a small link on the right, `planner.recompute.short` with the full text as its label and hint; "Routes offered", a segmented row 1 2 3 bound to `store.alternatives`, above the cards; then the error if any, the cards of the routes and the light profile). While a route is computing a small ring (`.result__spinner`) takes the place of the "Recompute" button and there is no loading text in the panel (the badge on the map says it, and is the live region); and the actions bar `.panel-footer`, outside the scrolling `.tab-route` so it never scrolls away: the save form of `SavedRoutes` (name and button on one row) or its "Saved" notice, and "Clear all". The bar only exists while the Route section shows and there is a point, and is hidden when the phone sheet is a peek. **Panel width** (wide screen): the right edge is a separator button `.panel-resize` in a 0.5 rem gutter of its own (the panel's right padding, so it never covers a scroll bar); pulling it widens the panel from 336 px (21 rem) to 720 px at most (`--panel-width`), a double click or Home gives the original width back, the arrow keys move it by 24 px; the width is kept in `localStorage` (`voie-libre.panel-width`) and told to the map driver (`setSideInset`) so that the fit buttons and the views keep clear of the panel. The result header keeps the height of the "Recompute" button so the ring that replaces it does not shift what follows. The planner styles are split in `planner.scss`, `planner-route.scss` and `planner-phone.scss` (the budget of a component style). **The planner sheet** (see `docs/features/mobile-sheet.md`) has three heights, `SheetState` `peek` (handle and a one-line summary of the selected route), `half` (50% of the map area) and `full` (all of it, the map hidden): the handle follows the finger (`vlSheetDrag`, `core/gestures/sheet-drag.ts`: live height in px, then the release with its speed), `snapTo` (`sheet-snap.ts`, pure) settles on the nearest height or, for a flick (0.5 px/ms), the next one in its direction; a tap or the up and down keys step through them (`nextState`, `stepState`); the CSS animates the change of height (none with `prefers-reduced-motion`); a touch of the map takes `half` back to `peek`; choosing a tab raises the sheet to `half`. `SHEET_PEEK_REM` (planner.ts) must match the peek height in planner.scss. **Full screen** (`FullscreenMap`, `core/fullscreen`): a button beside undo and redo on the map (phone only) hides the header, the offline bar (`App` host class `map-fullscreen`) and the sheet (`panel--gone`), leaves the map buttons and the same button to come back; no browser full screen API (it does not exist on iPhone), not remembered. **Light profile in the sheet** (`ProfileMini`, `profile-mini.ts`): on a phone the strip under the map (`vl-elevation-panel`) is not shown at all and this one shows under the routes in the sheet: the coloured curve (3.5 rem) and one line, distance, ascent and descent (`profile.mini`); no cursor, selection, legend or surface; hidden above 40 rem. On a wide screen the same component, with `compact` (curve only), fills the folded profile bar between the title and the chevron, so a folded bar is never empty. The profile bar starts **folded** (curve only); a tap or a swipe up opens the whole profile. The curve comes from `profilePaths` (`elevation-profile.ts`, shared with `ElevationPanel`).

## Undo and redo

(`PlannerStore`, buttons and keys in `Planner`; see `docs/features/undo.md`): every change to the route being planned (points, clear, profile, alternatives, loop mode, length and climb of a loop by distance) pushes a `Snapshot` (inputs plus the routes on screen, or `null` routes when they were not those of the points: `routesFor` holds the signature they were computed from) on a stack of `HISTORY_DEPTH` = 20. `undo()`/`redo()` restore it without any `POST /route` (the inputs are marked as restored); a snapshot without routes computes as for any change. Ctrl/Cmd+Z undoes, Ctrl/Cmd+Shift+Z and Ctrl+Y redo, ignored in text fields, selects and while the loop dialog is open. `loadSaved` empties the history; opening a saved route or importing a GPX is not undoable. An edit made before the previous one's route is in place is never local (`lastEditFromRoute`).

## Place search

(API `geocoding/`, `routes/geocoding.ts`; web `apps/web/src/app/search`; see `docs/features/search.md`): `Geocoder` interface, `PhotonProvider` (public server by default, `GEOCODER_URL`; only the API calls it). `GET /geocode?q=&lang=&lat=&lon=` and `GET /geocode/reverse` (rate limited, `GEOCODE_RATE_LIMIT_MAX`). The panel has Start and End fields (`PlaceField`: combobox, 300 ms debounce, disabled offline through `NetworkStatus` and while there is no start) and a reverse button (`PlannerStore.reverse`: the whole list of points reversed, stops included, a full recompute; a loop with two stops or more goes round the other way, `canReverse` is false for a loop with fewer); picking a place calls `setStart`/`setEnd`, `setLabel` and `PlannerMapDriver.centerOn`. Each stop is a `PlaceField` too, between the two (a place picked there moves the stop; a handle on its left, made of the grip dots and the stop's number, reorders it: the field gets `bareMarker`; a button on the right removes it). A "+" between each pair of fields opens an empty field there (`Planner.newStopAt`, the index the stop will take; closed when the points change), for a stop to search. An empty field offers "My position" as its first choice, which sets that point from `LocationStore` (asking for the position if needed). Place names live in `PlannerStore.labels`, keyed by coordinates (with `shortOf`: the short name the API gives each place, `Place.short`: its own name when searched, its town or village for an address or a click) (so they follow their point through undo, reorder and swap, and never recompute a route; not stored in saved routes). `PointNamer` reverse-geocodes the start and the end when they have no name (click, drag, menu, position), once per place, never offline; failures keep the coordinates. Errors are translated under `planner.search.errors.*`.

## Points on ways

(`apps/web/src/app/planner/snap-to-way.ts`, `way-snapper.ts`, `apps/web/src/app/core/map/way-tiles.ts`; see `docs/features/reverse-fit-snap.md`): on Road and Gravel a point placed on the map (click, map menu, marker drop, waypoint pulled out of the route, each place of a live drag) lands on the nearest way the profile can use (`usableBy`: classes of the Protomaps `roads` layer), within `SNAP_MAX_METERS` (100) and `SNAP_MAX_PIXELS` (24, `PlannerMapDriver.metersPerPixel`); with none that close the point is refused (`Planner.refused`, message `planner.snap.refused`; a refused drop cancels the drag) and during a live drag the route stays on the last valid place. Trail is never snapped; nor are places from the search, "My position", imports, or places where the basemap has no tile. The ways are read from the zoom 14 tile around the point (`WAY_TILE_ZOOM`: lower zooms leave small roads out) through the map's own PMTiles reader (`basemapTileReader`, offline copy first, no other server), decoded with `@mapbox/vector-tile` and `pbf`, behind the `WAY_TILES` token (`null` reader, so no snapping, while there is no real map: tests set a fake). `WaySnapper.peek` answers at once from the tiles already read, `snap` reads them first; the ghost marker shows the landing place (`PlannerMapHandlers.ghostAt`).

## Profile choice

(`apps/web/src/app/planner/profile-select.*`): `ProfileSelect`, a select-only combobox (the focus stays on the button, `aria-activedescendant`) where each profile has a title and a description (`planner.profile.<id>.title` and `.description`); a native select cannot show two lines per option.

## Elevation profile

(`apps/web/src/app/planner/elevation-profile.ts`, `elevation-panel.*`): `buildProfile` (pure: cumulative distance, grade over a 50 m window) and `ElevationPanel` under the map. The chart is coloured by grade bands (`GRADE_BANDS`, `gradeRuns`; the route line on the map keeps its colour). Dragging over the chart (or Shift+arrows) selects a stretch: `stretchStats` gives its distance, ascent, descent and average grade, `PlannerStore.stretch` holds it (dropped as soon as the selected geometry changes) and `PlannerMapDriver.setHighlight` draws it on the map; a click or Escape clears it. Nothing moves the map by itself: a button beside the selection's figures ("Zoom on the map") calls `PlannerStore.fitStretch`, and a "Show the whole route" button in the map's control column (`MapView.canFitRoute`/`fitRoute`) calls `PlannerStore.fitSelectedRoute`; both put a `ViewRequest` (`animate: true`, the map glides) that `Planner` hands to `PlannerMapDriver.fitRoute(geometry, animate)`. The shared cursor is `PlannerStore.cursor` (index in the selected geometry): the panel sets it on pointer or keys, `Planner` sets it from `PlannerMapDriver.onHoverRoute`, and an effect shows it as a dot through `setCursor`. **Descent colours** (see `docs/features/profile-colours-selection.md`): `gradeRuns` and `profilePaths` take `colourDescents`; when false a descent takes band 0 (the flat colour), climbs keep theirs. `DescentColours` (`descent-colours.ts`, `localStorage` `voie-libre.descent-colours`, never sent) says it per profile: off for road and gravel, on for trail, until the user changes it with the "Colour the descents" checkbox beside the legend; the chart and `ProfileMini` both follow it. **Selection bubble**: a selected stretch shows `.bubble` over the chart (distance, ascent, descent, grade on one line, and the zoom button as an icon), centred on the stretch and leaning on its edge near either end; its pointer events stop there so they never start or end a selection; the sentence under the chart is visually hidden (for screen readers) while a stretch is selected.

## Surface of the route

(API `routing/surface.ts`, web `planner/route-surface.ts`, `core/map/surface-categories.ts`; see `docs/features/surface.md`): `RouteResult.surfaces` and the `POST /route` response carry one character per segment of the geometry (`geometry.length - 1`): `p` paved, `c` cycleway, `u` unpaved or rough (cobbles included), `s` path, `?` unknown. `classifyWay` reads BRouter's `WayTags` (the surface first, then the way class), `surfacesFromMessages` lines the messages up with the geometry by their end coordinates and leaves `surfaces` out when they do not fit. `trimSpurs` and the "avoid the way out" join keep it in step. Web: `PlannedRoute.surfaces` is optional (imported files, routes saved before, shared routes have none), `applyStretch` splices it like the geometry (`spliceSurfaces`; it is dropped if the stretch has none), saved routes store it. `ElevationPanel` draws a bar under the chart on the chart's distance scale with the share of each category (`surfaceShares`); the checkbox "Surface of the route" of the layer switcher (`MapLayers.surface`, on by default) has `Planner` call `PlannerMapDriver.setSurfaces`, which draws the selected route in the categories' colours over its line (`surfacesToGeoJson`). A route without surfaces (saved before, imported, shared) says so (`PlannerStore.surfaceMissing`: a note under the chart and in the switcher) and offers "Calculate the surface": `PlannerStore.recompute` computes the route again from its points (`recomputeCount` makes `RoutePlanner` run with the same inputs), one step of history, so Undo brings the saved route back, and a failure keeps the route on screen (`takeRefresh`, `setLocalEditError`); `canRecompute` is false for a route from a place to itself without a loop mode, which gets a note and no button. Saved routes keep the loop mode they were computed with (`SavedRoute.loop`, optional: `PlannerStore.savable` gives it, `loadSaved` restores it and the restored signature includes it, so opening still computes nothing); loops saved before that kept none and stay as they are; opening a route still never computes.

## User position

(`apps/web/src/app/location`): the user shares it with the "My position" button on the map; it stays in memory (`LocationStore`: status, fix, error code), never stored, logged or sent to the API. The source sits behind the `GEOLOCATION` token (browser `watchPosition`; a fake in tests, a Capacitor plugin later). `PlannerMapDriver.setLocation` draws a blue dot, the accuracy circle (`accuracyCircle`, a map layer) and a cone when `coords.heading` is known, and moves the view to the first fix only. "My position" in the panel and the map menu adds a point at the fix like a click would (`addPoint`). Errors are `LocationErrorCode`s translated under `location.errors.*`; the button is disabled outside a secure context.

## GPX import

(`apps/web/src/app/import/gpx-import.ts`, button in `saved-routes`): `parseGpx` (DOMParser, `querySelectorAll`: live collections are quadratic in jsdom) reads the first `<trk>` (segments joined) else the first `<rte>`; geometry thinned to 5000 points, climb with a 3 m threshold, duration estimated per profile. No elevation on every point → `ascentMeters: null` (type `number | null` on `PlannedRoute`/`SavedRoute`): the profile is hidden, sharing is disabled, `buildGpx` gets `withElevation: false`. Errors are `GpxImportError` codes translated under `gpxImport.errors.*`.

## Relief

(API `relief/`, `routes/elevation.ts`; web `relief/elevation.service.ts`): `ElevationProvider` interface, `CopernicusElevationProvider` reads Copernicus GLO-30 GeoTIFFs from `RELIEF_DIR` with `geotiff` (one window read per tile, bilinear, `null` outside the tiles or on no-data). `POST /elevation` (max 5000 points, `ELEVATION_RATE_LIMIT_MAX`). The web app calls it only when the user asks to compute the climb of an imported route (`ElevationService.forGeometry`, gaps interpolated, refused under 80% coverage); `RouteStore.setElevation` stores the result. Jest transforms the ESM-only dependencies of `geotiff` (see `jest.config.cts`). The real-data spec skips itself without the tiles.

## Credits

`PlannedRoute.elevationSource` (`'srtm'` for BRouter routes, `'copernicus'` once the climb was computed from tiles; absent for an imported file's own elevations) is stored with the saved route and shown under the profile (`profile.source.*`).

## Local storage

(`apps/web/src/app/storage`, `saved-routes`): saved routes live in IndexedDB (native API) behind the `RouteStore` interface, injected with the `ROUTE_STORE` token (SQLite can replace it under Capacitor). Only the selected itinerary is stored, with a `schemaVersion`; ids are 10 random characters. Opening one goes through `PlannerStore.loadSaved`, which must never trigger `POST /route` (`RoutePlanner` skips inputs matching the restored route until the user edits). Storage failures are `RouteStoreError` codes translated under `saved.errors.*`; the planner stays usable without storage.

## GPX and FIT export

(`apps/web/src/app/export`): `buildGpx` (pure, GPX 1.1, one `<wpt>` per route point with translated names, then one track) and `buildFit` (`fit.ts`, pure, no dependency: a FIT course file with `file_id`, `course` (running for Trail, cycling otherwise), one `lap`, timer events, one `record` per geometry point and one `course_point` per stop; times are made up from the estimated duration; no altitude when the climb is unknown) turn a saved route's stored geometry into a file on the device. The "Export" button of a saved route opens the choice of a format (`exportingId`, `exportAs`); the download goes through the `FILE_DOWNLOADER` token (text or bytes; browser link now, Capacitor share later). Never built by the API. `fit.spec.ts` reads the file back with `fit-file-parser` (dev dependency only). **Laps**: a loop (end exactly on its start) has a number of laps from 1 to 20 (`SavedRoute.laps`, set in the export panel through `RouteStore.setLaps`, absent for one lap), with the total distance and climb shown; the GPX track repeats the loop (`export/laps.ts`), the FIT course writes one lap per turn (`buildFit(route, stops, laps)`) with distance and time going on; a route that is no loop always exports one lap.

## Offline

(`apps/web/src/app/core/offline`, `ngsw-config.json`): `@angular/service-worker` (production build only) prefetches the app shell and the i18n files, and keeps the basemap's glyphs and sprites (`dataGroups`, matched on any host by the `/fonts/**` and `/sprites/**` patterns of `ngsw-config.json`). The PMTiles archive is far too big to copy, so the user keeps **areas** (`OfflineBasemap`, panel `OfflineMap`; see `docs/features/coverage.md`): the corridor of 5 km each side around the route on screen (`corridorTiles`, `AREA_BUFFER_METERS`) or the view on screen (`MapViewport`, `viewBox`), zooms 0 to 14 (`core/offline/area-tiles.ts`, pure). `plan` samples tiles of the basemap and of the relief to estimate the size and checks the room (`navigator.storage.estimate`); an area above `AREA_MAX_BYTES` (1 GB) or `AREA_MAX_TILES` is refused (`too_big`); `keep` reads every tile through the PMTiles reader with a `RecordingSource`, which stores each byte range it got (header, directories, tiles) in a Cache Storage cache of its own (`voie-libre-area-v2-<id>`, key `url?vl-range=offset-length`); the list of areas (name, size, box, relief or not) is in `localStorage`. `OfflineFirstSource` reads the kept range first (`caches.match` looks through every area cache) and the network otherwise, so the map needs no network inside a kept area; removing an area deletes its cache; a cache the browser evicted drops its area from the list; the cache of the first version (whole archive) is deleted when found. The relief tiles of the area come along when the server has a relief archive (a 404 means none). Check offline with `npm run serve:prod` (`scripts/serve-static.mjs`: static files with an `index.html` fallback; the service worker does not run in `npm run dev`). `AppUpdate` + `vl-update-prompt` offer to reload when the service worker has a new version ready (never reload by themselves). When the network cannot carry a request, the service worker answers 504: the API error mappers treat 504 as network/unavailable.

## Saved routes list

the name button is stretched over the whole card (`::after`), so a click anywhere opens it; when the route on screen is unsaved work (`PlannerStore.unsaved`: points whose inputs differ from those of the route last saved or opened, `markSaved`, `savedSignature`) a confirmation comes first; a saved route opened and left alone, one just saved, or an edit that was undone, is replaced at once. Hovering a card shows its trace through `PlannerStore.preview` and `PlannerMapDriver.setPreview` (no view change). The steps in the planner panel are reordered with their grip (a button; see `docs/features/reorder.md`): pointer events, not native drag and drop, so mouse and finger behave alike (`Planner.onGripDown`, `reorder` signal, `numberOf` gives each row's future place as its CSS `order`: the rows show the new order while dragging, the numbers and the "+" stay (the "+" inert), the help bar says the route is computed again, Escape or a cancelled pointer changes nothing); Arrow Up/Down move a stop at once and a live region announces it. Release or key calls `PlannerStore.reorderPoint` (a full recompute, undoable). **Name proposed for a route** (`planner/route-name.ts`, `saved-routes`; see `docs/features/route-names.md`): the name field proposes `A → B`, `A → B via S`, `A → B via 3 stops`, `Loop around A` or `Around A` from the short names of the places (`autoRouteName`, keys `saved.autoName.*`), `Road, 41 km` while a name is unknown; the proposal follows the route until the user types in the field, and never again for this route; emptying the field saves the proposal; clearing the route or saving brings the automatic name back; a name already taken gets the date, then ` (2)`. Only the start and the end are looked up (`PointNamer`: a lookup running is cancelled only when its place stops being an end), so a stop has a name only when it was picked by search.

## Sharing

(API `routes/shared.ts`, `db/shared-routes.ts`; web `sharing/`): no account. `PUT /p/{id}` creates a shared route under the id drawn on the device and returns a delete token once (only its SHA-256 is stored); shared routes are **immutable** (an existing id answers 409, no update); `GET /p/{id}`, `GET /p/{id}.gpx?lang=`, `DELETE /p/{id}` with `Authorization: Bearer <token>`. PUT is throttled hard (`SHARE_RATE_LIMIT_*`) and capped (`SHARE_BODY_LIMIT_BYTES`, 5000 geometry points, 20 points). The token stays in the local record (`SavedRoute.share`), never in a URL or on screen. The share button is hidden for now (`SHARING_ENABLED` token, default `false`); the API and the code stay. Sharing is always an explicit user action; deleting a shared route unshares it first. `/p/:id` in the web app (`SharedRoutePage`) opens a link through `PlannerStore.loadSaved`, without computing or storing. GPX building and the id alphabet live in `libs/shared` (used by both).
